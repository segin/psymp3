# Architecture Overview

PsyMP3 is a cross-platform audio player with a software-rendered UI, asynchronous media loading, on-demand decoding, FFT visualization, and optional desktop integrations such as MPRIS and Last.fm.

This file is the compact architectural map, and reflects the tree as of 2.0-RC5. Older, implementation-heavy subsystem notes — parts of which still describe the SDL2-era tree — live in [docs/ARCHITECTURE_DETAILS.md](docs/ARCHITECTURE_DETAILS.md).

```text
│   ├── codecs/      # Audio decoders
│   ├── core/        # Display, surfaces, fonts, FFT, lyrics, file dialog, about

```

## Media Pipeline

```text
[Audio File / HTTP Stream]
           |
           v
   [MediaFile::open] -> [MediaFactory]     # content detection, format dispatch
           |
           v
     [DemuxedStream]                       # owns handler + demuxer + codec
           |
           +-> [IOHandler]  (File / HTTP / Memory)
           +-> [DemuxerFactory] -> [Demuxer] -> [MediaChunk]
           +-> [AudioCodecFactory] -> [AudioCodec] -> [AudioFrame]
           |
           v
       [PCM Frames]
           |
           +-----------------+
           |                 |
           v                 v
     [Audio Output]     [FFT / UI]
```

PsyMP3 is chunk-driven. Containers are parsed into compressed `MediaChunk`s, codecs decode on demand, and decoded PCM is buffered only far enough ahead to support smooth playback and responsive interaction. A decode thread fills the PCM buffer ahead of the SDL callback; the callback drains it, taps the FFT from the raw PCM, then applies volume and the equalizer to the copy going to the device — so the spectrum stays volume- and EQ-independent. Samples are `AudioSample` (full-scale `int32_t`) throughout.

One `Stream` sits outside that path: `ChainedStream` concatenates several files into a single stream, opening each through `MediaFile::open` in turn. It requires every track to share a sample rate and channel count, aggregates length/position/seek, and answers cover art for the track currently playing; its other tag getters describe the first track.

**Metadata flow.** Demuxers that understand their container's tags populate `Demuxer::m_tag` with the in-house Tag framework (`include/tag/`): Ogg, FLAC and Matroska/WebM store a `VorbisCommentTag` (Matroska's SimpleTag names already follow the Vorbis convention; an album-scoped `TITLE` is remapped to `ALBUM`), and the MP3 demuxer parses the leading ID3v2 and trailing ID3v1 blocks into an `ID3v2Tag`/`ID3v1Tag` (merged as `MergedID3Tag` when both exist, ID3v2 taking precedence per field). `DemuxedStream`'s metadata getters (`getArtist`/`getTitle`/`getAlbum`/`getMusicBrainzID`/…) read `m_tag` first and fall back per-field to the base `Stream` implementation (TagLib `FileRef`) when a field is missing, so the titlebar, MPRIS, Last.fm, and Discord all see the same values. `getArtist`/`getTitle`/`getAlbum` check one more place in between — the `StreamInfo` the demuxer reports — and that middle step is how containers whose demuxers build no `Tag` get their metadata out: ISO BMFF's `udta`/`ilst` and RIFF/AIFF's `LIST INFO`, `NAME` and `AUTH` chunks both arrive that way. Playlist entries (`track`) run the other way: TagLib parses the file first, and a resolver registered by `mediafile.cpp` re-opens it through the demuxer stack only when TagLib fails, filling just the fields still empty — so an untagged or TagLib-hostile file still gets a real length and artist in the playlist. ID3v1 fields are decoded ISO-8859-1 → UTF-8 at parse time, matching ID3v2's encoding-0 handling.

## Primary Subsystems

- `src/codecs/`: Decode AAC (LC/HE-AACv1/HE-AACv2/xHE-AAC), AC-3/E-AC-3, FLAC, MP3, MP2, ALAC, MLP/TrueHD, Opus, Vorbis, Speex, PCM-family, G.711, and G.722 streams into PCM. The whole AAC family — AAC-LC, HE-AACv1 (SBR), HE-AACv2 (SBR + Parametric Stereo) and xHE-AAC (MPEG-D USAC, audio object type 42) — goes through one `AACCodec` driving FDK-AAC. faad2 used to serve the first three, but it stops at object type 27 and could not decode USAC at all, so a second decoder had to be carried beside it; FDK decodes all four, and in the comparisons done at the time handled SBR and especially Parametric Stereo more cleanly besides. `BoxParser` still names a USAC stream separately (both share esds objectTypeIndication 0x40, so it reads the audioObjectType out of the AudioSpecificConfig), because that is what Media Info spells xHE-AAC and what decides whether loudness normalisation is applied — xHE-AAC carries programme loudness metadata and expects it, the rest do not. The profile shown in Media Info comes from the decoder's reported object type after a frame has decoded, not from the AudioSpecificConfig, because SBR and PS are usually signalled implicitly. FDK's calls live behind a plain-C shim (`codecs/aac/fdk_aac.cpp`) built as its own translation unit, keeping `<fdk-aac/FDK_audio.h>` out of the unity build — the same treatment stb_vorbis gets. The shim also asks the linked library what it implements (`aacDecoder_GetLibInfo` and the `CAPF_*` flags), because FDK can be built with profiles removed while keeping the same API and pkg-config name — Fedora's `fdk-aac-free` is exactly that. A stripped build would otherwise decode an HE-AAC file to its core rate with no SBR, at the right duration and half the bandwidth, with nothing to say so; instead the capability set is logged once and a stream the build cannot decode is refused at init. Vorbis uses the vendored stb_vorbis (`third_party/stb`, compiled as its own C object) in pushdata mode: the Ogg demuxer delivers de-paged packets, and `VorbisCodec` wraps each one back into minimal Ogg page framing (real lacing/continuation and page CRC — stb validates CRCs during its post-seek resync) before feeding the decoder. No libvorbis at link time; libogg remains for container parsing.
- `src/demuxer/`: Parse Ogg, ISO BMFF, RIFF/WAV, AIFF, Matroska/WebM, FLAC, MP3, MLP/TrueHD, AC-3/E-AC-3, and raw streams into codec-ready chunks and metadata. Self-framing formats (MP3, MLP/TrueHD, AC-3) use "null" demuxers that walk their own frame headers.
- **Raw PCM byte order travels with the stream.** `StreamInfo::big_endian_samples` says how the samples are stored, because AIFF holds them big-endian while RIFF/WAV and AIFF-C `sowt` hold them little-endian, and the PCM codec assembles each sample in the stated order rather than the host's. Reading one as the other is not a subtle error: it decodes to static. Reads are also aligned to whole frames — a chunk ending mid-frame loses the partial sample and misaligns every chunk after it, which is inaudible at 16-bit stereo only because the read size happens to divide evenly by that frame size.
- MP3 is handled by bundled `minimp3` via `MiniMP3Codec` and `MP3NullDemuxer`; MP2 by bundled `kjmp2` (compiled into `MP2Codec`'s own translation unit); and ALAC by Apple's bundled Apache-2.0 decoder (`third_party/alac`). No external runtime dependency remains for any of the three.
- MLP and Dolby TrueHD are handled by a bundled decoder (`third_party/mlp`, Apache-2.0 — see "MLP/TrueHD" below) via `MLPCodec` and `MLPNullDemuxer`; no external dependency.
- G.722 is decoded in-tree by `codecs/pcm/G722Decoder.cpp` via `G722Codec`; no external dependency. It replaced spandsp, which is LGPL-2.1-only and so would have forced the relink obligation of LGPL section 6 onto the statically linked Windows executables, and which dragged in libtiff and its image dependencies for the sake of four symbols. The decoder is written from the Recommendation and was developed against spandsp, matching it bit-for-bit in both the 16 kHz and 8 kHz output modes, on encoded audio and on arbitrary octets alike. At 56 and 48 kbit/s that match was a mistake: spandsp reads a right-justified 7- or 6-bit code there, while the Recommendation keeps the 64 kbit/s octet and only ignores the lowest one or two bits of its lower band (§1.3, §1.4.4), which is what PsyMP3 does now; spandsp is gone from the tree. `G722Codec` always decodes mode 1 at 16 kHz. G.722 signals its mode out of band, which no container carries, and without that signal the Recommendation says to use mode 1 (§1.3). `ChunkDemuxer` likewise reports a G.722 WAV as 16 kHz whatever `nSamplesPerSec` says, since a header's 8000 describes the octet rate. The decoder's 8 kHz output, the lower sub-band alone, is not part of the Recommendation and is reachable only through `G722Decoder`'s constructor. What checks the decoder now is the Recommendation's own Appendix II: `test_g722_conformance` runs its digital test sequences in all three modes. ITU distributes them only inside its software package, so `tests/fetch_g722_testvectors.sh` downloads them, and the test skips without them. The bitstreams captured from spandsp remain in `tests/g722_fixture.h` as test input. Two details cost the most time and are easy to get wrong: G.722 Table 9 limits the sub-band signals `rL` and `rH` to −16384..16383 rather than the full int16 range, and clipping them there before the synthesis QMF is what keeps loud passages correct; and the QMF's output is limited as well (ACCUMC/ACCUMD). A sum that overshoots is clipped to full scale. The decoder used to wrap it round to the opposite polarity instead, which is what matching spandsp had required.
- `src/tag/`: The in-house tag framework — ID3v1/ID3v2, Vorbis comments, the merge rules above, and cover-art extraction (`ImageUtils`). It is what demuxers populate and what `Stream` consults before falling back to TagLib.
- `src/io/`: The `IOHandler` abstraction and the large-file-safe offset contract used across the pipeline. `FileIOHandler` opens UTF-8 paths; `HTTPIOHandler` streams over HTTP via `HTTPClient`/`URI`, determining seekability from the response headers and degrading to forward-only streaming when the server offers no ranges; `MemoryIOHandler` backs in-memory fixtures and unit tests.
- `src/audio.cpp`: Own the SDL audio device, decode thread, PCM queue, and FFT feed. The FFT tap folds whatever the stream carries down to one mono signal — a straight copy for mono, L+R for stereo, and the average of every channel past that (a branch that was missing, so surround streams showed silence) — and converts only the frames SDL actually handed the callback.
- `src/dsp/Equalizer.cpp`: Real-time 7-band biquad equalizer applied to the output PCM (see below).
- `src/widget/`: Render the software UI, manage event routing, z-order, floating windows, and overlays.
- `src/core/display.cpp` and `src/core/surface.cpp`: Present the software-rendered UI through SDL surfaces.
- `src/core/font.cpp`: Render all UI text into PsyMP3-owned surfaces — SheenBidi (vendored) resolves bidirectional reading order, HarfBuzz shapes each run against the face that has its codepoints, and FreeType rasterises the resulting glyphs. HarfBuzz is a hard dependency; see "Text rendering" below.
- `src/core/lyrics.cpp` + `src/widget/ui/LyricsWidget.cpp`: Load a track's `.lrc` (or `.srt`/plain-text) lyrics from beside the media file, decode them to UTF-8, and render the current and upcoming lines as an overlay driven by playback position.
- `src/debug.cpp`: The logging framework. Every subsystem logs to a named channel (`audio`, `player`, `demux`, `chunk`, `http`, `ac3`, …), with `parent:child` sub-channels; `--debug <channels>` (or `--debug all`) enables them and `--logfile` redirects output to a file. With no channel enabled the calls are cheap no-ops.
- `src/system.cpp`: Platform services — config/storage paths, thread naming and priority — plus the Windows-only shell integration: a hidden IPC window that broadcasts now-playing to other applications, taskbar progress through `ITaskbarList3`, and the thumbnail-toolbar transport buttons, whose messages arrive through `win32MessageHook` rather than as SDL events.
- `src/player.cpp`: Coordinate playback state, loading, preloading, GUI updates, and integration points.
  The startup playlist populator runs on a background thread and expands command-line `.m3u` / `.m3u8` files inline so mixed file-and-playlist argument lists preserve user order.
- `src/playlist.cpp` / `src/track.cpp` / `src/mediafile.cpp`: The playlist model. `Playlist` owns the entries, the playback cursor, shuffle order and a generation counter the Playlist Manager polls for reloads, and offers block edits (`insertEntries`, `removeTracks`, `moveTracks`) that keep cursor and shuffle order consistent under one lock; `track` is one entry's path plus cached tags; `MediaFile` is the format registry that decides what the choosers, drag-and-drop and directory recursion accept.
- `src/core/FileDialog.cpp`: Native "open file" chooser (`PsyMP3::Core::FileDialog`) backed by a build-time-selected toolkit (Qt 6/5/4/3, GTK+ 4/3/2, or Win32 comdlg32). Isolated in its own `libpsymp3-filedialog.a` convenience library so the GUI-toolkit headers/flags reach no other translation unit; compiled out entirely when `configure` finds no toolkit, leaving the file-chooser menu items greyed out.
- `src/widget/ui/MenuBarWidget.cpp`: In-app, software-drawn menu bar (see below).
- `src/core/compression/` and `src/core/utility/` hold small shared helpers (LZ77, Base64, UTF-8 utilities) built as their own convenience archives. `src/core/persistentstorage.cpp` is a SQLite-backed store that nothing else currently references.

## In-App Menu Bar

The menu bar is a single widget, `MenuBarWidget` (namespace `PsyMP3::Widget::UI`), not a tree of per-menu / per-item widgets. Menus and items are plain data structs it paints and hit-tests itself.

- **One overlay widget per bar.** The main `MenuBarWidget` spans the width of the logical surface (it is created 640×400 over a 640×404 surface) and is added as a top-most window at `ZOrder::MAX` — above all UI including toasts (`ApplicationWidget::getWindowZOrder` special-cases it). Its `Surface` is transparent everywhere except the top bar and any open dropdown/submenu, so clicks and hover pass through to the widgets beneath when nothing is open. The class doubles as a per-window bar: the equalizer window and the Playlist Manager each embed a client-sized `MenuBarWidget` as an ordinary child. Only the main bar sits at `ZOrder::MAX`.
- **Data, not widgets.** A private `Menu` struct (name + cached bar x/y/width) holds a `std::vector<Item>`. The public `Item` struct is a tagged-by-convention row — a *leaf* (`action`, optional `checked` predicate for a radio dot, optional `enabled` predicate whose false paints the row grey and swallows the click, optional right-aligned `shortcut` hint), a *separator*, or a *submenu* (self-nesting `std::vector<Item>`). Built via the `leaf()` / `sep()` / `sub()` factories.
- **The bar can be more than one row.** `layoutBar()` flows the titles and wraps to another row when the next will not fit the width, so the bar's height is `barHeight()` (`rows × BAR_H`), not the `BAR_H` constant — content placed below it must use the accessor. `resize()` re-flows and repaints, which is how a bar embedded in a resizable window keeps up with it.
- **Immediate-mode paint.** `rebuild()` repaints the entire overlay from current state on every change: transparent fill, opaque bar, then the open dropdown and any expanded submenu. Text is drawn with the FreeType LCD/ClearType path (`Font::RenderLCD`); `&` in a label marks a mnemonic drawn underlined, and `shortcut` renders right-aligned in its own reserved column.
- **Self-contained hit-testing.** Because there are no child widgets, `handleMouseDown` / `handleMouseMotion` / `handleMouseUp` do the geometry directly via shared pure helpers (`barHitTest`, `dropdownRect`, `submenuRect`, `itemAt`, `popupWidth/Height`) so draw and hit-test never disagree. Leaves activate on *release*, the classic menu protocol: a press only highlights the item, so press-drag-release from a bar title selects in one gesture and a press can slide off the item to cancel. A release anywhere else keeps the menu open, which is what makes a plain click on a bar title open it. `handleMouseDown` returning `false` when nothing is open lets input fall through.
- **Keeps the UI live.** Since the bar is painted and dispatched by the normal widget/event loop rather than a native OS menu, the visualizer keeps animating while a menu is open (no modal message pump). Menu actions call the same player methods as the corresponding keys; `checked` predicates reflect live state.
- **Player wiring.** `src/player.cpp` assembles the `Item` trees and calls `addMenu()` for four menus: **File** (Open Tracks… / Clear Playlist / Queue Track Next… / Queue Track… / Play Now… / Media Information… / Exit, with the file-chooser entries greyed out when no toolkit was found), **Playback** (Pause / Previous Track / Restart Track / Next Track / repeat and Shuffle state / Volume Up and Down / Equalizer… / Playlist Manager…), **Settings** (FFT Mode, Delay, Intensity and Target FPS submenus, then 2x Zoom, Show Debug, Last.fm Credentials…, Discord Presence) and **Help**. Each key-mirroring leaf calls a named `Player` action method (`volumeUp`, `setIntensity`, `toggleZoom`, …) that the keyboard switch calls too — menus invoke the real action directly rather than injecting synthetic key events. The Playlist Manager window builds a second `MenuBarWidget` of its own, with a File menu of Load Playlist… / Save Playlist… / Persist Playlist.
- **Keyboard driver.** `MenuBarWidget::handleKey(SDL_keysym)` is the single entry point, called from `Player::handleKeyPress` — but not first, and not unconditionally. An already-open dropdown is handled ahead of everything else (the equalizer window's bar if one of its menus is open, else the main bar), and a *closed* bar may only be opened when no widget holds the mouse capture, since an open menu eats the release and would wedge a seek-bar drag. When the equalizer window is the active window its own bar is offered Alt chords first, because "&Presets" and "&Playback" both answer to Alt+P. While a menu is open it is *modal for the keyboard*: Up/Down move the selection (skipping separators, wrapping via `stepSelectable`), Right enters a submenu or advances to the next top-level menu, Left backs out of a submenu or moves to the previous menu, Enter/Space activate, Esc backs out one level then closes, and a bare mnemonic letter jumps to/activates the matching item. Every key is consumed while open so none leak to the global shortcut table.

## Text rendering

`Font` wraps one FreeType face and caches what FreeType charges for. Glyph advances are memoised per codepoint on the simple path — shaped text takes its advances from HarfBuzz instead, and loads its glyphs unhinted, because the autohinter snaps stems to the grid and that pulls the joins of a connecting script apart — and rasterised glyphs are cached as *coverage* rather than finished pixels, so a single entry serves every foreground/background pair a caller asks for. The coverage of a whole line is accumulated into one buffer and blended once at the end, rather than each glyph being blended and written on its own: glyph boxes are allowed to overlap, and in a joining script they always do, so writing finished pixels per glyph let a later glyph's empty edge erase the stroke that held the word together. The glyph cache runs two generations: when the live one fills it becomes the previous one and a hit there is promoted rather than redrawn, because clearing outright discards exactly the glyphs on screen.

Faces are chained. `vera.ttf` (DejaVu Sans) carries no CJK, Kana or Hangul, so an optional `extra.ttf` is consulted for codepoints the primary lacks; on Windows it supplements the embedded copy without replacing it. For the scripts that join or reorder it is consulted *first*, winning even where the primary does have the codepoint. DejaVu Sans is the case in point: it carries Arabic letters and the GSUB rules to substitute them, so it looks supported, but its glyphs are not drawn to connect, and the result is correctly shaped letters that still do not touch. No shaper can fix that; only a font can. The test is `needsComplexLayout`, the same codepoint check that routes a string into the shaper, so plain Latin, Cyrillic, monotonic Greek and CJK keep the primary and adding a fallback for one script cannot silently restyle the rest of the interface. The primary still fixes line height and baseline so mixed scripts share one grid, and when no face has a codepoint the primary's `.notdef` box is drawn. Resolution is deterministic per codepoint, which is what lets the advance and glyph caches stay keyed by codepoint alone. Shaped text cannot be: one codepoint may yield several glyphs or several codepoints one, so `m_shaped_cache` is a third map, keyed by face index and glyph id packed together.

HarfBuzz is a hard dependency (`pkg-config harfbuzz`, no opt-out). SheenBidi is vendored verbatim in `third_party/sheenbidi` and built as its own archive from a single translation unit, so it can opt out of the tree's `-Werror` — the same treatment stb_vorbis and the MLP decoder get. It is Apache-2.0, like those.

## FFT / Visualizer

`FastFourier` (`src/core/fft.cpp`) owns the time-domain window the audio callback fills and the spectrum the UI reads; `fft_draw.cpp` and `SpectrumAnalyzerWidget` turn it into the display. Four implementations are selectable at runtime — `mat-og`, `vibe-1`, `neomat-in`, `neomat-out` (`FFTMode::Original`/`Optimized`/`NeomatIn`/`NeomatOut`) — through **Settings → FFT Mode** or `--fft`; the selection is an atomic because the UI thread writes it while the audio thread reads it. The callback converts only the frames SDL delivered and zero-fills the rest of the window, so the spectrum decays to silence rather than repeating the last block.

## MLP / Dolby TrueHD

Meridian Lossless Packing and its Dolby TrueHD successor decode through a bundled decoder, `third_party/mlp`. Like `third_party/alac` (Apple's decoder) and `third_party/sheenbidi`, it is **Apache-2.0 rather than ISC**: it is derived from [truehdd](https://github.com/truehdd/truehdd) (truehd 0.7.1), Copyright © 2025 Rainbaby, and carries that licence forward; the file header states the changes, as Apache-2.0 section 4(b) requires. No published MLP specification is available without a Dolby licence, and the openly documented descriptions stop at the container layer, so there was no ISC-compatible route to the decoder internals.

- **Third-party licences ship with the binary.** `THIRD-PARTY-LICENSES.txt` is the source of truth; `scripts/gen-third-party-licenses.sh` wraps it into the committed `include/core/third_party_licenses.h`, so `psymp3 --licenses` and the About window can print the full set from a self-contained executable. Edit the `.txt` and regenerate; commit both.
- **Self-containerizing, like MP3.** Every access unit starts with a four-byte header giving its own length in 16-bit words, so the stream needs no container to be framed. `MLPNullDemuxer` walks that chain and hands one access unit per `MediaChunk` to `MLPCodec`.
- **The decoder is its own translation unit.** `codecs/mlp/mlp_decoder_impl.cpp` compiles `third_party/mlp/mlp_decoder.cpp` once and is linked straight into the binary: it is listed in `psymp3_SOURCES` in both build modes, and `psymp3.final.cpp` does not `#include` it — the same treatment `stb_vorbis_impl.c` and `codecs/aac/fdk_aac.cpp` get. Both the codec *and* the demuxer need it: the demuxer decodes the first access unit to learn the sample rate and channel layout rather than re-implementing the major sync, because the channel count comes from the restart header rather than the sync itself.
- **Also carried in MP4 and Matroska.** An `mlpa` sample entry is MLP or TrueHD inside an ISO container, which is what Dolby-branded `.m4a` files use; `BoxParser` maps it to the same codec, and `SegmentParser` maps Matroska's `A_TRUEHD` and `A_MLP` to it as well. The `mlpa` entry is followed by a `dmlp` configuration box, but nothing needs reading out of it, for the same reason the raw demuxer decodes an access unit: the stream states its own rate and channel layout in the major sync. Those files also tend to write the audio sample entry's sample rate as a plain integer rather than 16.16 fixed point, since MLP reaches 192 kHz and the fixed-point field stops at 65535 — `BoxParser` accepts either.
- **Seeking lands on a major sync.** The decoder cannot start mid-stream, so `parseContainer` makes one linear pass over the access unit headers, counts them for an exact duration, and indexes the major syncs (subsampled to one per 500 ms, since they recur about every 106 ms). A seek binary-searches that index and resumes at the sync at or before the target. Unlike the AC-3 demuxer it does not report that landing as a granule, so up to half a second of audio before the target plays rather than being trimmed.
- **Two deliberate departures from the reference**, which is a conformance checker rather than a player. The recorrelator's 24-bit range assertions are dropped: encoders do run slightly past full scale on near-clipping material and those samples still decode correctly, so enforcing the check would discard audio a reference decoder keeps. `MLPCodec` clamps instead of wrapping when it scales the 24-bit samples up to the pipeline's full-scale S32, since a wrapped peak is an audible click. Timing, FIFO and lossless-check validation are left out entirely — they diagnose a stream, they do not affect its samples.
- **Verified bit-exact** against an ffmpeg reference decode: 308,454 access units, 24,676,310 samples, zero differences.

## AC-3 / E-AC-3 (A/52)

**AC-3 and E-AC-3 play from every container PsyMP3 demuxes except AVI, which has no demuxer.** Written from ATSC A/52:2012, which is publicly available (it is not vendored; [docs/atsc-a52.txt](docs/atsc-a52.txt) links the current edition), so unlike MLP this one is ISC and in-tree. `ffmpeg` is used strictly as an oracle: it generates streams to decode and its own PCM output is what a decode is diffed against. Its source is copyleft, under the LGPL or the GPL depending on how it is built, and is never read; neither is liba52's.

- **Five of `src/codecs/ac3/`'s pieces take a frame from its header to its mantissas.** `AC3FrameHeader` reads `syncinfo()` and `bsi()` (syntax in §5.3.1–5.3.2, meaning in §5.4.1–5.4.2); `AC3Exponents` the D15/D25/D45 differential exponents of §7.1; `AC3BitAllocation` the seven-step parametric routine of §7.2.2, with the eleven tables of §7.2.3 (Tables 7.6–7.16) in `AC3Tables.h`; `AC3Mantissas` the quantizers and grouping of §7.3; and `AC3Block` walks Table 5.3 and drives the other four. The directory holds fourteen sources in all — the transform, downmix, frame decoder, codec adapter and the Annex E tools below.
- **The header is the only way to tell AC-3 from E-AC-3.** `bsid` sits at bit offset 40 in both, where §E2.1 puts it for that purpose, and its value selects which of two incompatible header layouts the rest of the frame uses: Table 5.2 for bsid 0–8, Annex E's Table E1.2 for 11–16. `AC3FrameHeader::Flavour` records which, so Media Information can name the stream before anything is decoded. bsid 6, Annex D's alternate syntax (§D2.1), needs nothing extra: Table D2.1 puts its new fields where Table 5.2 has the two 14-bit time codes, so it is read the same way and plays through the ordinary path. bsid 9 and 10 are values §E2.3.1.6 says a decoder cannot decode and must mute. They are read with Table 5.2's layout so the stream can still be named AC-3, but `isDecodable()` refuses them, so they are never decoded.
- **A frame cannot be decoded one block at a time.** Six audio blocks share one syncframe and most fields in a block are optional, with "reuse the last" as their default: exponent strategies, coupling, the allocation parameters and the delta bit allocation all carry forward. `AC3FrameState` is that working memory, and block 0 is special in several places — it may not say "reuse", and an absent delta bit allocation there means "apply none" rather than "keep the last".
- **Bit budget as the correctness test.** Nothing in the frame states where the mantissas end; the decoder has to arrive there by allocating exactly the bits the encoder spent. So the test that mattered while bringing the parser up is where the sixth block lands: a correct parse stops with 18 bits left — `auxdatae`, `crcrsv` and the 16-bit `crc2` — plus whatever the encoder padded. A single misread bit anywhere scatters that landing, which made it a far sharper instrument than listening to the output. Nothing in the tree asserts that landing. The block parser refuses a block that reads past the end of its frame, or that states a value A/52 rules out, such as a bandwidth code above 60 or a reserved strategy, but nothing checks where the sixth block stops.
- **The tables are the thing to distrust.** Four transcription errors came out of A/52's printed tables: `floortab[7]`, `fastgain[7]`, `baptab[7]` and `hth[fscod][48]` at all three sample rates were each wrong, most of them page furniture, such as a page number or a column header, read as data. Layout is no guide to which tables are at risk: in A/52:2012, floortab (Table 7.10) is a single column that breaks across pages 70 and 71, fastgain (7.11) a single column on one page, and hth (7.15) and baptab (7.16) two-column tables that each fit on one page. Shape-checking the extracted values against the spec text mechanically, rather than reading them, is what caught them.
- **`AC3FrameDecoder` turns a syncframe into PCM; `AC3Codec` adapts it to the pipeline.** The inverse transform (`AC3Transform`, §7.9) is checked by perfect reconstruction — exact to about 1e-5 in practice, with the test failing at 1e-3 so float rounding cannot make it flaky. The codec does not assume one syncframe per chunk. An MP4 sample or a Matroska frame can hold more than one: in E-AC-3, dependent substreams and other programmes are syncframes of their own (§E2.3.1.2), carried alongside the independent substream they go with. RIFF hands its data chunk over in slices cut to a multiple of `block_align`, which encoders set to anything, so a slice can end part way through a syncframe. Input is therefore buffered and every whole syncframe in it decoded.
- **Output goes to one fixed SDL speaker layout (`AC3Downmix`).** SDL reads a channel count as a fixed layout — 3 is 2.1, 4 quad, 5 is 4.1, 6 is 5.1 — with no centre speaker below six, so coded channels cannot simply be packed in order. `ac3OutputChannels()` picks the smallest layout with a speaker for every coded channel (3/2 takes six channels with or without its LFE, and a single surround plays through a pair at −3 dB), and `AC3OutputMatrix` renders any arrangement into any layout: straight to a speaker where there is one, otherwise mixed down by §7.8.1 with the stream's own centre and surround levels, normalised so no output channel sums past unity. The layout is fixed before decoding from the channel count the demuxer declares, since that is what the audio device is opened with, so a stream that decodes to a different arrangement, or changes arrangement mid-stream, is mixed to fit instead of being read at the wrong stride. MP4 declares that count from the `dac3`/`dec3` box, not the sample entry's ChannelCount.
- **Containers.** Raw `.ac3`/`.eac3` through `AC3NullDemuxer`, which will not believe the 16-bit sync word until the next frame starts where the first says it ends, does not advance the clock for dependent E-AC-3 substreams, and seeks a frame short of its target — rebuilding the overlap and the E-AC-3 history the codec's reset dropped — then reports where it landed so `DemuxedStream` trims to the target; WAVE through format tag `0x2000`, including `WAVE_FORMAT_EXTENSIBLE` files, which `ChunkDemuxer` resolves through the SubFormat GUID (anything over two channels arrives that way); MP4/M4A through the `ac-3`/`ec-3` sample entries; Matroska through `A_AC3` and `A_EAC3`. E-AC-3 is named `eac3` wherever it can be told apart, so Media Information can say so. AVI has no demuxer in tree.
- **Verified end to end against the oracle.** `tests/generate_ac3_corpus.sh` puts bit-identical syncframes in every container — AVI included, for the day an AVI demuxer exists — and that identity is what the script itself checks. Each file decodes through the production demuxer registry and `AudioCodecFactory` to exactly ffmpeg's sample count, lining up at zero lag, at roughly 60–77 dB SNR against its 16-bit reference — that reference's own quantization floor. That decode comparison is run by hand against ffmpeg; `make check` covers the unit tests, not the corpus.
- **E-AC-3 is the same decoder with a frame layer in front.** `EAC3Frame` parses the full `bsi()` and `audfrm()`, which hoists into the frame most decisions AC-3 makes per block: which optional block syntax exists, coupling and exponent strategies for all blocks (per block, or one Table E2.10 row per channel), frame SNR offsets, and the AHT, transient and spectral-extension-attenuation flags. The block parser takes that frame as an optional argument rather than being duplicated, because an E-AC-3 block differs from an AC-3 block only in what the frame lets it omit. Frames of 1, 2, 3 or 6 blocks are handled; the demuxer, codec and clock count only program 1 (independent substream 0), as §E3.8.1 requires, and skip dependent substreams and other programmes.
- **The Annex E tools each live in their own file:** `EAC3SpectralExtension` (§E3.6), `EAC3AhtMantissas` with `EAC3AhtTables` (§E3.4), `EAC3EnhancedCoupling` (§E3.5) and `EAC3TransientPreNoise` (§E3.7). Spectral extension synthesises after rematrixing, since it copies each channel's finished low band — Annex E does not place it explicitly, and that is the only order in which the copy is of the channel. An AHT channel reads all six blocks' mantissas the first time it is reached in a frame. Its inverse DCT is the orthogonal one printed in §E3.4.5, √2·Σ R_j X(j) cos(j(2m+1)π/12) with R_0 = 1/√2; the plain-text rendering of the standard drops both radicals. The noise sources — §7.3.4 dither, spectral extension noise, and enhanced coupling's decorrelation offsets — are all xorshift32. The standard asks only for a distribution, but the values fill adjacent bins, and a shift register stepped one bit per value correlates neighbouring bins, which shapes the noise in time until it pumps at the block rate. Dynamic range control (`dynrng`, §7.7.1) is applied by default, as the standard requires, before each block's inverse transform.
- **E-AC-3 output is held back behind decoding.** Decoded samples go into one planar line per coded channel, placed by absolute sample position, and are rendered into the output layout as they are released. Enhanced coupling rebuilds a block from the blocks before and after it, so a frame's last block waits for the next frame. Transient pre-noise processing (§E3.7) rewrites up to 1022 samples before a transient, and a frame may place its transient in the frame after it, so corrections are queued by absolute position, applied once their transient has decoded, and output is released 1022 samples behind the newest decoded sample; a correction could otherwise begin in samples already handed on. AC-3 releases each frame whole. The hold is in when samples are handed over, not where they fall: output is contiguous and `flush()` drains it, which `DemuxedStream` does only once every buffered chunk has been through the codec, and the stream does not end until a flush comes back empty. The codec stamps output from a running count of what it has emitted. The noise generators deliberately survive the per-frame state reset; restarting them every frame would be audible.
- **What the oracle can and cannot check.** ffmpeg's E-AC-3 encoder emits only the core Annex E path at every bitrate and layout: no AHT, spectral extension, enhanced coupling or transient pre-noise processing, and no dynamic range words. Core E-AC-3 matched ffmpeg's decode when it was brought up (72.5 and 80.8 dB, zero lag, exact counts, through raw, MP4 and Matroska); that comparison is run by hand, while the other tools are verified by unit tests against the standard's own arithmetic, including an identity for enhanced coupling — analysing three consecutive blocks of a signal and regenerating the reference channel at unit gain returns the middle block's coefficients.
- **Still to do:** E-AC-3 at the reduced sample rates (24, 22.05 and 16 kHz), which is recognised but not decoded, because A/52 does not say which hearing threshold its bit allocation uses and FFmpeg does not decode it either; an AVI demuxer; the Lt/Rt and Lo/Ro downmix levels a bsid-6 stream may carry, which Annex D leaves optional for decoders (§D3) and which the header parser skips as the time codes they replace, so such a stream is downmixed by its `cmixlev` and `surmixlev` like any other AC-3 stream; rendering E-AC-3 dependent substreams beyond 5.1 (optional per §E3.8); the heavy compression word `compr`, which is for decoders asked to constrain peaks; and dialogue normalisation (`dialnorm`), which §7.6 places at the system level beside the volume control and which is not applied.

## Matroska / WebM

`.mka`, `.mkv` and `.webm` play. `MatroskaDemuxer` sits on four pieces that each do one thing and are tested on their own: `EBMLReader` for the element grammar, `SegmentParser` for Info and Tracks, `BlockParser` for frames and lacing, and `CueIndex` for seeking. What is left in the demuxer itself is the cluster walk, a queue (a laced block yields several frames at once), the `Tags` reader that fills the `Tag` the rest of PsyMP3 sees, and enough state to resume after a seek.

- **EBML is the substrate** (`demuxer/matroska/EBMLReader`). Every Matroska file is EBML elements nested arbitrarily: an ID, a size, and either a payload or more elements, with both ID and size written as variable-length integers whose width lives in the leading zeros of their first byte. Two details in that encoding fail silently rather than loudly, and both are pinned by tests. An **ID keeps its marker bit and a size strips it** — the EBML magic is `0x1A45DFA3`, which is how the specification writes it and how a lookup table must; read as a size the same bytes are `0x0A45DFA3`. And a size whose **every value bit is set means unknown**, not enormous: that is how a muxer writing to a socket emits a Segment whose length it cannot yet know, arriving as `01 FF FF FF FF FF FF FF`. Reading it as a length walks off the end of the file.
- **The reader is deliberately not a `Demuxer`** — no streams, no seeking by time, no codecs — which is what lets it be tested against literal bytes in memory through `MemoryIOHandler`. `decodeVInt` is static and takes a buffer rather than the handler, which is what lets `BlockParser` reuse it against an in-memory frame — for the track number, for the first EBML-laced size, and for each signed delta after it.
- **Segment parsing** (`demuxer/matroska/SegmentParser`) reads the EBML header, `Info`, `Tracks` and `SeekHead`, and stops at the first `Cluster`; the header elements are all it wants and the clusters are where the file's bulk is. It records where that cluster starts and where the Segment's payload begins, since cue and cluster positions are relative to the latter.
- **Timestamps are in ticks, not milliseconds.** `TimestampScale` gives nanoseconds per tick and every timestamp in the file is in those — cluster times, cue times, block offsets. It is essentially always 1,000,000, making a tick a millisecond, and it is still read rather than assumed: a file that sets it differently and is read as if it had not is wrong by exactly that ratio. A file that states zero is treated as though it had stated nothing, since a zero scale would flatten every timestamp in the file to zero.
- **CodecID maps to the names `CodecRegistry` dispatches on** (`codecNameForId`), and a codec PsyMP3 has no decoder for maps to nothing *on purpose*. DTS is the notable absence and it is common in `.mkv` (AC-3 and E-AC-3, commoner still, are decoded in tree); returning empty lets a file be refused by name rather than opened and failed at its first packet. `A_AAC` matches with or without a profile suffix, since one decoder covers the family and the profile comes back out of the AudioSpecificConfig anyway.
- **Track selection** skips video, anything the file has marked disabled with `FlagEnabled`, and anything undecodable, and prefers a track flagged `FlagDefault` over file order — which is how a multi-language release says which track to play. The filter governs only which track is played; every audio track is still reported.
- **Units are converted at the `StreamInfo` boundary.** `CodecDelay` is nanoseconds of decoder startup; PsyMP3 counts that in sample frames, as it does for AAC priming, so Opus's 6,500,000 ns at 48 kHz becomes the 312 frames ffprobe calls `initial_padding`. `OutputSamplingFrequency` beats `SamplingFrequency` where both are present, because SBR codes a track at half the rate it plays at and taking the coded rate would play it at half speed. `A_PCM/INT/BIG` sets `big_endian_samples`, the same flag AIFF needs and for the same reason.

- **Blocks carry one frame or several** (`demuxer/matroska/BlockParser`). A block's timestamp is *signed* and relative to its cluster, because a frame may legitimately precede the cluster that stores it; read unsigned, such a frame lands about a minute into the future at a millisecond tick. Lacing packs several frames into one block in three ways, and the two that store sizes each leave the **last frame implicit**, as the remainder. Xiph writes each size as a run of `0xFF` bytes plus a terminator; EBML stores the first size as a VINT and every later one as a **signed delta** from its predecessor, biased by half the range its width can hold — 63 at one byte, 8191 at two; fixed stores no sizes at all and requires the payload to divide evenly among the frames. A block with *n* frames stores *n−1* sizes, so a single-frame laced block stores none, and reading one regardless silently eats the first byte of the frame. None of these sizes are cross-checked by the format, so a truncated or hostile block can describe frames running past what was read; parsing fails rather than handing back a frame that points outside the buffer.

- **Header stripping is undone; every other content encoding is refused.** Matroska's `ContentEncodings` lets a track declare that its frames were transformed before storage. The common case is header stripping (`ContentCompAlgo` 3): mkvmerge removes bytes every frame shares, such as an MP3 frame's sync word, and records them once in `ContentCompSettings`. `SegmentParser` collects those bytes (for frames, for `CodecPrivate`, or both, as `ContentEncodingScope` says; stacked steps in ascending `ContentEncodingOrder`), `toStreamInfo` puts the private part back in front of `CodecPrivate`, and `MatroskaDemuxer` prepends the frame part to every frame. zlib, bzlib and LZO compression, encryption, and the "next encoding" scope are not supported, and a track that uses any of them is never chosen: fed to the decoder as stored, its frames would decode to noise. zlib is the schema default, so a `ContentCompression` without an algorithm counts as zlib.

- **`DiscardPadding` is dropped in `DemuxedStream`.** A `BlockGroup` can say how much of its Block's decoded audio is padding: at the end when positive, at the start when negative. FFmpeg writes it on the last block of Opus, Vorbis, AC-3 and MP3 tracks. The demuxer reads the whole group first, since the value may follow the Block, converts it to sample frames at the track's output rate, and marks the Block's first or last frame with it (`MediaChunk::padding_head_frames` / `padding_tail_frames`). Leading padding is dropped like an encoder's priming. Trailing padding is harder, because a codec may still be holding part of that block: the AC-3 decoder keeps some output back, and so does the MP3 decoder. `DemuxedStream` therefore holds the padded block's output until the flush has returned the rest, and then cuts the padding off the end of the lot.
- **An undecodable audio codec means the file does not open**, which is how every other container behaves rather than a Matroska special case: `DemuxedStream::selectBestAudioStream` takes the first audio stream and `AudioCodecFactory::createCodec` returns nullptr for a `codec_name` it does not know, so the open fails. `getStreams()` therefore reports every audio track but puts the preferred one first — a DTS + FLAC `.mkv` leads with FLAC and plays, while a DTS-only one leads with DTS, fails to create a codec and is skipped, with the codec named in the `demux` log. Nothing is hidden, so Media Information still sees the tracks that cannot be played.

- **`SeekHead` is the index of the Segment's own top-level elements**, and following it is not optional. `Cues` are written after the clusters, often at the very end of a large file, so nothing finds them without it; and a muxer may put `Tracks` there too, in which case a parse that stops at the first `Cluster` reports a file with no tracks at all. Its positions are offsets from the start of the Segment's payload, not from the file.
- **Seeking is a `Cues` element, or a scan when there is none** (`demuxer/matroska/CueIndex`). Cues are optional and plenty of files ship without usable ones, so a walk of the cluster headers stands in: each `Cluster`'s size says where the next begins, making it proportional to the number of clusters rather than to the size of the file. Cue entries **for other tracks are ignored** — ffmpeg cues only the video track of a `.mkv`, and seeking audio by video keyframe positions is wrong quietly rather than loudly. A lookup returns the last entry at or *before* the target, since the decoder can only start at a cluster; landing after would skip audio outright. **The landing is then trimmed off.** `MatroskaDemuxer` reports granule positions — the landing after a seek, the last chunk handed out otherwise, both in samples — so `DemuxedStream::seekTo` sets its discard counter to the requested target and drops the audio between the two as the frames come through, the way it already did for Ogg and AC-3. Reporting no granule is not a neutral default here: it left the counter at zero, so the seek played from the cluster boundary while reporting the target as its position, up to a whole cluster early.

The landing reported is the cluster's *own* `Timestamp`, read from the cluster header at seek time, and not the index entry's time. A `Cues` entry pairs `CueTime`, which is the timestamp of a *block*, with the position of the cluster holding it, and that block need not be the cluster's first. Reading restarts at the cluster head regardless, and `DemuxedStream` labels frames from a counter anchored on the reported landing rather than from the chunk's own stamp, so naming the later time would keep the audio between the two and mislabel it for the rest of the track, not just for one frame. This is a guard rather than a repair of anything yet observed: the `.mkv` files to hand cue only their video and subtitle tracks — 1072 and 11803 CuePoints respectively, not one of them for an audio track — so `parseCues` collects nothing for the selected track and the scan fallback is what actually runs. That fallback stores each cluster's own `Timestamp` and is self-consistent by construction, so only the `Cues` path ever needed this correction. `CueRelativePosition`, which would name the block inside the cluster and let the seek land closer still, is defined and read by no one.
- A cluster's `Timestamp` must precede its blocks but **need not be its first child** — ffmpeg writes a CRC-32 ahead of it — so the scan walks children until it finds one, stopping at the first block. Reading only the first child finds the CRC and concludes the cluster is untimed, which leaves the entire index empty.

- **Tags are scoped by `TargetTypeValue`.** A `TITLE` at target 50 is the album's and at 30 the track's, so without reading it every release overwrites its own track title with the album name — only the album-scoped `TITLE` is renamed to `ALBUM`; everything else keeps the name Matroska gave it. Values are appended rather than assigned, which keeps a multi-valued `ARTIST` value-separate the way the rest of PsyMP3 expects. `Tags` are reached only through `SeekHead`: the Segment walk stops at the first cluster and does not collect them itself, and unlike `Cues` there is no scan to fall back on, so a file that omits the `SeekHead` entry is read with no tags.
- **Format detection needs the magic in three places.** `DemuxerRegistry` and `DemuxerFactory` keep separate signature tables and every format is listed in both; the playback path probes through `DemuxerFactory`, since that is where `DemuxedStream` builds its demuxer. `MediaFactory` keeps a third, and that is the one `MediaFile::open` matches against. In the first two a signature is a byte vector, so the EBML magic is written `{0x1A, 0x45, 0xDF, 0xA3}` like every other entry; in `MediaFactory` signatures are `std::string`s, and the EBML magic there needs an explicit length rather than a bare literal, which would stop at the first byte.

Known gaps: `A_MS/ACM` (a `WAVEFORMATEX` in `CodecPrivate`) is unmapped and DTS has no decoder in tree, so a `.mkv` whose only audio is DTS is skipped. `Attachments` are stepped over rather than read, so a `.mkv`'s embedded cover art never reaches the tag framework or MPRIS. Chapters are not parsed at all.

## Equalizer

A 7-band graphic equalizer, opened from **Playback → Equalizer…**.

- **DSP (`src/dsp/Equalizer.cpp`).** A cascade of seven RBJ peaking biquads (60/150/400/1k/2.4k/6k/15k Hz), one filter state per channel, applied in place to the output PCM inside the SDL audio callback — *after* the volume scaling, so that at sub-100% volume the attenuation leaves headroom and positive band gains are far less likely to clip loud material. (The FFT tap runs before both volume and EQ, so the spectrum stays volume- and EQ-independent.) It is real-time-safe like `Audio::m_volume`: the UI thread pushes band gains via atomics and bumps a dirty counter; the audio thread owns the coefficients and history and recomputes lazily. Filter history is zeroed on seek/track-change through a two-stage reset: `requestReset()` arms an atomic from any thread, and `latchReset()` — which the audio callback calls while holding the same PCM buffer mutex the resetters hold — moves it into the flag `process()` consumes, so a reset armed after a buffer was drained cannot fire one buffer early. `Audio` owns one `Equalizer` and exposes thin `setEq*`/`getEq*` forwarders; the EQ is disabled by default (a no-op).
- **State ownership.** `Player` holds the canonical band gains + enabled flag and re-applies them to each new `Audio` (mirroring volume), so settings persist across track changes — and across restarts; see "Persistent State".
- **UI (`src/widget/ui/EqualizerWindow.cpp`).** A draggable in-app window (a `WindowFrameWidget` hosted in `m_random_windows`) whose client is a `LayoutWidget` of one `SliderWidget` fader per band (live dB readout + frequency label), an `EqualizerCurveWidget` preview, an enable checkbox, a Volume row (a horizontal `SliderWidget` over 0..1 with a percentage readout, which drives `Player::setVolume` and is reflected back by `EqualizerWindow::setVolume()` when the volume changes elsewhere — keyboard or MPRIS — without echoing it), and an embedded `MenuBarWidget` with **Presets** (built-ins) and **User Presets** (five `.psymp3eq` slots in the config dir; a *Save* submenu stores into a slot). Moving a fader routes through one change path that updates the curve, the readout, and the DSP.
- **Curve preview.** `EqualizerCurveWidget` (a `DrawableWidget`) plots the band gains as a smooth curve using `core/BezierCurve.h` — a Catmull-Rom spline through the control points expressed as cubic Bézier segments.
- **New toolkit pieces.** `SliderWidget` (vertical/horizontal fader), `EqualizerCurveWidget` (curve canvas), and `core/BezierCurve.h` (reusable Bézier/smoothing helpers) were added for this feature and are usable elsewhere.

## Persistent State

`psymp3.conf` (key=value, in the platform config dir) is the general settings file: `volume`, `eq_enabled` and `eq_band_<n>` sit alongside `zoom`, `target_fps`, `shuffle`, `loop_mode`, `show_debug`, `discord_presence`, `persist_playlist` and `session_track`. It is read at construction and rewritten at shutdown, and also when one of its toggles changes, so a crash does not lose a setting the user just picked from a menu.

When `persist_playlist` is on, the playlist itself is saved to `session.m3u8` in the same directory on exit and restored on the next launch; `session_track` records where playback was, and the background playlist populator withholds the start event until enough entries exist to cover that index.

Two other files live beside it: `lastfm.conf` (0600, credentials and the issued session key) and `scrobble_cache.xml` (0600, pending scrobbles), plus the five `.psymp3eq` user EQ preset slots.

## Widget Toolkit

The software-rendered UI (`src/widget/`) imitates Windows 3.1, and since 2.0-BETA2 it does so to the pixel, with a real keyboard focus model layered on top.

- **Win3.1 rendering fidelity.** `ButtonWidget` paints the reference push button: 1px black outline with notched (transparent) corners, 2px white top/left highlight, stepped 2px grey bottom/right shadow, 24px tall, label centered over the bevels. The bold double border marks the button Enter will activate — the focused button while any button holds focus, otherwise the window's *default* button (`setDefault`) — and migrates between them as focus moves; a focused button also shows label-bounded focus dots, so it carries both. `ScrollbarWidget` is 17px wide with 17×17 end pieces whose outlines merge into the control's frame, a fixed square thumb, stem-and-head arrow glyphs (3×3 stem, 7→5→3→1 head), a 50% white/grey dithered shaft, and an inverted-dither pressed-track indicator.
- **Press gestures.** All push buttons (including the titlebar minimize/maximize/restore buttons drawn by `WindowFrameWidget`) follow one gesture model: sink on mouse-down with capture, track hover while held (drag off = pop up, drag back = re-sink), fire only on release inside. Scrollbar arrows additionally sink their glyph 1px down-right and auto-repeat while held (300ms initial delay, 60ms cadence, pausing while the cursor is off the button); track paging uses the same repeat clock, ticked once per frame from `recursiveBlitTo`.
- **Keyboard focus.** Focus is per-class static state (`TextInputWidget`, `ListViewWidget`, `ButtonWidget` each track their focused instance) rather than a central focus manager. `Player::handleKeyPress` routes keys through a fixed chain: an *already-open* dropdown first (the equalizer window's menu bar if one of its menus is open, else the main `MenuBarWidget`), which is modal for the keyboard; then Tab/Shift+Tab focus cycling; then the focused text input (which swallows everything except Alt chords and F-keys; Escape blurs; Ctrl+V pastes the system clipboard, filtered to one line), then the focused list (arrows move the cursor, Shift+arrows grow or shrink the selected run from its anchor, Enter fires `setOnActivate`, Delete fires `setOnDelete` with the whole run), then the focused button (Enter activates immediately; Space sinks and fires on release), then Enter on the window's default button. Only then — and only while no widget holds the mouse capture, so a key can never open a menu mid-drag — do the *closed* menu bars get their Alt+mnemonics: the equalizer window's while it is the active window, then the main menu bar. Last comes the global shortcut table, which is where Ctrl+F4 (close the active frame) lives. Tab/Shift+Tab walk a DFS-collected list of focusable widgets (`collectFocusables`). Every mouse-down clears all three focus classes before the click is dispatched.
- **List selection.** `ListViewWidget` selects one contiguous run of rows between an anchor and a cursor; Shift+click and Shift+Up/Down extend it. Dragging a selected row moves the whole run, reported through `setOnReorder(first, last, to)`; every drop gap from the run's first row to just past its last shows no marker and is refused, so a run can never be dropped into itself. A plain click inside a multi-row run keeps it until release, so the run can be dragged, and selects just that row if no drag followed. The Playlist Manager applies Delete, Move Up and Move Down to the whole run through `Playlist::removeTracks` and `Playlist::moveTracks`, which repeat the single-track edits under one lock to keep the playback cursor and shuffle order; the same actions hang off the list's right-click menu (`setOnContextMenu`, which keeps a multi-row selection when the click lands inside it). The list also accepts *external* file drops: `setDropIndicator`/`externalDropHover` show an insertion bar at the hovered gap and auto-scroll the list while the pointer holds past an edge (`autoScrollTick`, clocked once per frame from `recursiveBlitTo` like the scrollbar's repeat timers).
- **Window frames.** `WindowFrameWidget` owns the titlebar, the L-shaped corner resize zones (outer edge + notch, with per-corner cursors), double-click on the control-menu box to close (a single click there raises the window and toggles the menu), and the control menu — which is an ordinary `UI::ContextMenuWidget` child (entries carry enabled flags, separators, and an accelerator column), not bespoke drawing. While the menu is open the system-menu icon inverts; clicking anywhere else dismisses it. Menu entries: Restore/Move/Minimize/Maximize/Close (Ctrl+F4), disabled to match window state; Move enters a pointer-follow move mode.
- **Blit model.** Top-level windows blit via `BlitTo`; children composite via `recursiveBlitTo` under `ClipRectGuard`. Overlay-ish children (context menus) render as real children of their frame so z-order and hit-testing stay inside the ordinary widget tree.

## MPRIS / D-Bus Integration

`src/mpris/` implements MPRIS2 as five cooperating components coordinated by `MPRISManager`; incoming method calls are dispatched, not just properties broadcast.

- **Component split.** `DBusConnectionManager` owns the bus connection and name; `PropertyManager` is the thread-safe property store (metadata, playback status, position with wall-clock interpolation while Playing); `MethodHandler` is the dispatch table for incoming calls; `SignalEmitter` batches and emits `PropertiesChanged`/`Seeked` from a worker thread (PropertiesChanged coalesces within a 50ms window; `batches_sent` counts the coalesced batches, while `signals_sent` counts every signal message put on the wire, Seeked included). `MPRISManager` wires them, registers the object path, and exposes the player-facing update API. Property changes are broadcast as a whole-snapshot `PropertiesChanged`: every update writes the store and then emits the complete Player-interface property set, never a changed-keys delta — so the store must always be written *before* the emit, or the signal carries the stale value.
- **The pump.** Incoming traffic is dispatched by `MPRISManager::processEvents()` — a non-blocking `dbus_connection_read_write_dispatch` called once per GUI iteration from `Player`, on the main thread because dispatched handlers call non-thread-safe `Player` methods. Nothing pumps autonomously: no pump, no replies. Outbound, `Player` pushes the play position into the property store about once a second while Playing; that deliberately emits no `PropertiesChanged` (clients read `Position` on demand, answered by the interpolating store), so the only position signal on the bus is `Seeked`, emitted when the user actually seeks.
- **Connection policy.** Connections are *private* (`dbus_bus_get_private`-style), never shared — libdbus caches shared connections and the session address globally, which made bus-restart recovery impossible. The session address is read from the environment on every connect. The well-known name `org.mpris.MediaPlayer2.psymp3` is requested with `DO_NOT_QUEUE`; if another instance owns it, the spec's `…psymp3.instance<pid>` fallback is registered instead (`getServiceName()` reports what was actually acquired, and cleanup releases that name).
- **Reconnection.** Automatic retries are budgeted and exponentially backed off; a successful reconnect resets the budget, and explicit caller-initiated `reconnect()` bypasses the backoff (`attemptReconnection(force)`). After reconnecting, the manager re-registers the object path on the new connection — a fresh connection carries none of the old registration.
- **Null-player mode.** Constructing `MPRISManager(nullptr)` is supported end-to-end (headless/testing): the `MethodHandler` is still created and answers commands with error replies while properties work normally, `isReady()` holds, and `initialize()` after `shutdown()` starts a fresh lifecycle.
- **Spec surface.** `org.freedesktop.DBus.Introspectable.Introspect` returns the complete MPRIS2 XML; the root interface includes `DesktopEntry`; `Properties.GetAll` on an interface without registered properties returns an empty dict per the D-Bus spec.
- **Cover art.** `mpris:artUrl` carries the track's embedded cover as an RFC 2397 `data:` URI -- the image itself, as KDE's Elisa publishes it -- so desktop media widgets can show it with nothing written to disk. `Stream::getCoverArt()` picks the front cover, else the first picture with data: from the in-house Tag framework first (ID3v2 `APIC`, FLAC `PICTURE`, Ogg `METADATA_BLOCK_PICTURE`), then TagLib 2's `PICTURE` complex property, which also reaches MP4 `covr` atoms. `ChainedStream` answers for its current track. `Tag::ImageUtils::dataUri()` takes the MIME type from the image's own header rather than the tag, since taggers mislabel — and it recognises only JPEG, PNG, GIF, WebP and BMP, so an image it cannot identify yields no URI at all. It also leaves out anything over 1 MiB: clients receive the URI whole with every metadata change. A track without art sends no `mpris:artUrl`, so the previous cover does not linger.

## Last.fm Scrobbling

`src/lastfm/` scrobbles via the Last.fm **Web Services API 2.0** (`ws.audioscrobbler.com/2.0/`), using PsyMP3's registered API key/shared secret (embedded in `LastFM.cpp`).

- **Auth.** `auth.getMobileSession` (username + plaintext password over HTTPS, request signed with the shared secret: MD5 over name-sorted `<param><value>` pairs + secret). The issued session key never expires; it is persisted as `session_key=` in `lastfm.conf`, after which the plaintext password is dropped from memory (and only ever needed again if the user revokes the app — error 9 clears the stored key so the next attempt re-authenticates). Hard auth failures — bad credentials (4), bad API key (10), suspended key (26) — disable scrobbling for the session instead of retrying.
- **Submission.** `track.scrobble` (one call per track, drained in batches by the background submission thread with exponential backoff) and `track.updateNowPlaying`. A `status="ok"` with an *ignored* verdict still counts as submitted — resubmitting can only be ignored again. API 2.0 has no removeNowPlaying call, so clearing (pause/stop, and unconditionally on destruction so exit never leaves a stale status) works by re-submitting the last-shown track with `duration=1`, replacing the live status with one that expires immediately.
- **Offline cache.** Failed/pending scrobbles persist across runs in `scrobble_cache.xml` (0600, like `lastfm.conf`), parsed and written with vendored pugixml.
- **MusicBrainz IDs.** `track` carries the recording MBID from the file's tags: `track::loadTags` reads TagLib's normalized `PropertyMap` key `MUSICBRAINZ_TRACKID` on its primary path and the custom Tag framework (`ID3v2Tag` reads the Picard `UFID:http://musicbrainz.org` frame and matches `TXXX` frames by description; Vorbis comments are generic already) on its decoder-fallback path. The submission-side accessors go the other way round: `Stream::getMusicBrainzID()` (and `DemuxedStream`'s override, which starts at the demuxer's own tag) consults the in-house Tag framework first and TagLib's `PropertyMap` only as a fallback. Scrobbles and now-playing updates pass it as `mbid` only when it is a well-formed UUID (`LastFM::isValidMBID`), and it round-trips through the offline cache.
- **Multi-artist credits.** A multi-valued artist tag (several Vorbis `ARTIST` fields, ID3v2.4 multi-value TPE1) is kept value-separate all the way through the demuxers and Tag framework; display strings join every artist (", "), while Last.fm submission uses the **first artist only** (the API has no multi-artist model — a joined credit lands on a nonexistent artist page). `Stream::getPrimaryArtist()` / `getMusicBrainzID()` are the submission-side accessors; the Player's scrobble/now-playing sites build their metadata-only `track` from the *stream* (not `track::loadTags`), so that is where submission metadata must be wired.
- **Credentials UI.** Settings → "Last.fm Credentials..." (a `WindowFrameWidget` dialog in `player.cpp`) edits username/password with a masked password field (`TextInputWidget::setPasswordMode`), and a Test button that runs a stateless `LastFM::testCredentials` handshake on a worker thread. The worker owns only a shared result block (never the dialog), so the window can be closed mid-handshake; the dialog polls that block once per frame. Only one test runs at a time, and the thread is kept joinable — not detached — reaped at the next test and joined in `~Player`, because a worker outliving `main()` races curl/OpenSSL static teardown. Saving rewrites `lastfm.conf` (dropping a stale `session_key` when the account or password changes) and recreates the `LastFM` instance; the old instance is destroyed *first* because its worker also writes the conf on auth success.

## Discord Rich Presence

`src/discord/DiscordPresence.cpp` shows "Listening to PsyMP3" via the Discord desktop client's local IPC (framed-JSON over `discord-ipc-N` — unix socket on POSIX incl. Flatpak/snap paths, named pipe on Windows; no external library).

- **Worker model.** Same shape as `LastFM`: public setters record a last-write-wins pending activity and notify; one worker thread owns all socket I/O, waking every 15s while Discord is absent, and re-sends the current presence after a reconnect. It dials out only when it actually has something to publish — an idle player with Discord not installed would otherwise sweep every candidate socket path on every wake. Updates are sent only on track change/pause/seek/stop — the progress bar is client-rendered from start/end timestamps. Visible updates are additionally floored at one per 4s (`kMinSendInterval`; Discord allows roughly 5 per 20s, and a held seek key would fire one every 100ms); updates queued inside that window collapse into the pending slot so the newest state is what goes out.
- **Activity shape.** Type 2 (Listening): `details`=title (filename stem for untagged files), `state`=artist (+" (paused)"), `name`=artist (an override so the compact member-list line reads "Listening to &lt;artist&gt;" rather than the app name), timestamps only while playing with known length, and — only when artwork resolved — an `assets` object carrying the Cover Art Archive image (`front-250`), the album as its `large_text` tooltip, and the PsyMP3 logo as the corner badge. The album rides on the artwork, so a track with no resolvable cover shows no album text either. Artwork is resolved on the worker thread in two steps: a tagged MusicBrainz *release* ID (`Stream::getMusicBrainzReleaseID()`, validated as a UUID) names a release URL, but it is used only when a probe finds the image actually there — plenty of releases have no front cover in the archive, and taking the tag's word for it left the best-tagged files with no artwork at all. Otherwise the worker searches MusicBrainz for the *release group* by primary artist + album, since the release group is the album as a whole while a single release is one of often dozens of regional pressings; the hit is accepted only at a relevance score of 85 or better (`kMinMatchScore`), because MusicBrainz always returns its best match however poor. Searches are rate-limited, retried on transient failures, and memoized one album deep. Strings are clamped to Discord's 2–128-byte limits on UTF-8 boundaries; absent fields are omitted, never faked.
- **Wiring.** `Player::updateDiscordPresence()` mirrors player state; called from `submitNowPlaying` (start/resume), pause, stop, and seek. Settings → "Discord Presence" toggles it (`discord_presence` in psymp3.conf). The application ID is a compiled-in constant (`PSYMP3_DISCORD_CLIENT_ID` env overrides for testing); empty ID leaves the worker dormant.

## Key Runtime Rules

- Public/private lock pattern: public methods acquire locks and delegate to `_unlocked` helpers.
- The widget tree is main-thread-only. Workers publish through atomics or a polled result block; nothing off the main thread touches a widget.
- The audio callback never blocks on decode or file I/O.
- Same-format track transitions reuse the live `Audio` object and device.
- `Audio` keeps decoded stream format separate from SDL's obtained device format so playback timing, seeks, and reuse decisions stay tied to source PCM instead of backend conversion details.
- Loader-thread prebuffering primes PCM before track handoff so both reused and recreated audio paths do not start from an empty queue.
- The decoder thread discards stale decode results after a stream swap, and again after a seek: `resetBuffer()` bumps a decode epoch, and a read that began before it is dropped together with its EOF latch — otherwise a decode in flight would re-latch EOF that the seek just cleared and end the track on a backward seek in the tail.
- The decoder thread and priming read and queue whole frames only. A read that ends inside a frame keeps the rest for the next read instead of dropping it — dropping it cut a gap into every read and rotated the channels of every 3-, 5-, 6- or 7-channel stream — and the buffer limits are sized in time, so surround streams get the same look-ahead as stereo.
- `Audio`'s PCM queue is `m_buffer` read through a cursor (`m_buffer_read`). The callback only copies and advances the cursor. Erasing the front of the vector moved the whole remaining queue on every callback, under the buffer lock: up to a quarter of a second of audio. The decoder thread reclaims the played prefix before appending, and only once that prefix is at least as long as what is still queued, so the vector stays within about twice the queue. Seeks and stream swaps reset the cursor with the queue.
- Playlist population stays asynchronous, and inline playlist arguments are flattened in place before later command-line media paths are appended.
- Text stays UTF-8 internally once it enters the process: command-line file arguments are normalized before playlist population, Unix file I/O opens `TagLib::String` paths through UTF-8 byte strings, SDL window titles receive UTF-8, and the FreeType font layer measures/renders decoded Unicode codepoints instead of raw UTF-8 bytes.
- Widget input is hierarchical, clip-aware, and capture-aware.
- The `I` key queues files chosen from a native dialog immediately after the current track, leaving the playing track undisturbed; `Ctrl+O` replaces the whole playlist with the chosen tracks and plays the first; the File menu's "Queue Track..." appends to the end. The `L` key plays a chosen file in place of the current track without touching the playlist, so the next track change resumes normal flow and forgets the override. All of these exist only when a file-dialog backend is compiled in; the menu items stay visible but greyed out otherwise.
- Dropping files onto the window (SDL `DROP_BEGIN`/`DROP_POSITION`/`DROP_FILE`/`DROP_COMPLETE`) accumulates the batch and expands it once on completion: directories are recursed for supported media files, `.m3u`/`.m3u8` playlists are expanded, unsupported files are silently ignored. Where the pointer lands decides the rest: over the open Playlist Manager's list the batch is inserted at the hovered gap (`Playlist::insertEntries`), leaving playback and the playback cursor alone, with a live insertion bar following the pointer and edge auto-scroll while it hovers past a boundary; anywhere else it replaces the playlist in one step and plays from its first track. A batch that expands to nothing changes nothing. Available even in builds without a file-dialog backend.
- Command-line options are parsed in `src/main.cpp`: `--fft <mat-og|vibe-1|neomat-in|neomat-out>`, `--scale` and `--decay` seed the visualizer; `--debug <channels>` / `--logfile` drive logging; `--test` and `--unattended-quit` are for automated runs; `--no-mpris-errors` silences D-Bus failures; `--version`/`-v`, `--licenses` and `--help`/`-h` print and exit. Everything else is a media path or playlist.
- There are two build modes and the sources list differs between them: the default builds each translation unit separately, while `./configure --enable-final` concatenates them into `src/psymp3.final.cpp` (one TU, far faster on a header change). A few objects are excluded from the unity build and compiled on their own — `stb_vorbis_impl.c`, `codecs/aac/fdk_aac.cpp`, `codecs/mlp/mlp_decoder_impl.cpp`, `core/sheenbidi_impl.c` — so a new source file must be added to *both* lists in `src/Makefile.am`.

## SDL3 Status

- The whole tree builds against SDL3 (Linux and all three Windows cross-arches); there is no SDL2 fallback.
- `Display` owns the SDL window and presents through the wrapped window surface; teardown order is guarded with `SDL_WasInit` so late destructors never touch a quit subsystem.
- Text input uses `SDL_EVENT_TEXT_INPUT`; SDL3's bool-returning APIs (`SDL_Init`, `SDL_LockSurface`, …) are used with their SDL3 semantics.
- Audio uses the SDL3 stream/device APIs. Tests run headless by setting `SDL_AUDIO_DRIVER=dummy` before `SDL_Init` (see TESTING.md); the application itself never selects a driver.
- Font rendering is FreeType-based, with the shared FreeType bootstrap living under `src/core/` (`TrueType` owns the process-wide `FT_Library`); SDL3 changed nothing here. Shaping and bidi (HarfBuzz + vendored SheenBidi) sit above it — see "Text rendering".
